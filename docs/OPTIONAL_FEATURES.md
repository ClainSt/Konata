2026-11-08：按用户决定停止应用插件路线，角色/声优与真人演职员改为内置可选功能。基础媒体库、刮削、播放、记录、备份与恢复仍属于核心。

## 设置与迁移

- 设置 → 扩展紧邻“关于”上方；仅提供“Bangumi角色/声优资料”和“TMDB真人资料”两个开关。
- 2026-11-08 UI 第二轮按用户新要求：全新配置默认开启 Bangumi 角色；已有明确关闭的偏好保留，损坏数据仍关闭。任一资料源开启后，“刮削服务”才显示角色栏总开关；打开角色栏后才显示 Bangumi 的角色 / 声优 / 关闭选择。删除旧的两张资料说明卡。
- 动画优先使用已开启的 Bangumi 展示；关闭 Bangumi 展示时可回退到已启用的 TMDB，真人作品使用已启用的 TMDB。关闭角色栏时不使用任何人物资料源，但保留所有开关和展示偏好。模式选择与扩展启停分别保存。
- 真人演职员复用现有 TMDB 凭据设置；动画从 Bangumi 获取角色与声优资料。服务请求失败可重试，有旧资料时优先保留用户编辑及可用的回退内容。

- 不删除用户媒体库、手工角色、排序或旧安装文件。旧文件仅用于回退，当前程序不提供插件安装、加载或执行入口。恢复媒体库不会自动启用扩展。

## 运行与资源边界

关闭时只保留少量开关偏好；不创建人物业务会话，不发起人物请求、下载图片或启动功能计时器。启用后也只在对应详情页实际使用时创建会话。

页面离开或功能关闭时，会话撤销监听、取消排队任务、强制关闭网络连接、停止计时器并清空图片字节缓存。图片组件撤下时取消自己的请求并驱逐自己的缩略图解码缓存，不清空核心共享图片缓存。异步旧结果不能重新写回界面或会话缓存。

扩展由 `lib/core/optional_features.dart` 的 `OptionalFeatures` 统一管理开关和活动作用域；`lib/core/optional_feature_scope.dart` 提供共用的资源登记、取消、定时器和有界 HTTP 请求。关闭开关时，管理器同步关闭该功能的所有作用域，随后通知界面。页面离开时主动关闭自己的作用域并从管理器注销。角色与真人演员均已接入，不再自行监听开关或分别维护 HTTP 客户端、计时器及取消信号。

新增扩展的业务入口通过 `settings.openScope(feature)` 申请作用域，再用 `scope.acquire(资源工厂, 释放函数)` 登记独占缓存、连接或订阅；提前结束使用 `scope.release(resource)`，页面结束调用 `scope.dispose()`。重复关闭不会重复释放，关闭后的资源工厂不会执行。共用请求入口为 `scope.readBytes`，定时器入口为 `scope.timer`；异步写回前检查 `scope.checkActive()`。资源释放函数应同步停止工作；需要异步收尾的资源仍须立即阻止后续请求与写回。业务特有的数据转换、域名白名单及容量限制留在对应功能中，共享核心播放器资源不交给扩展作用域释放。

每会话图片字节缓存上限 4 MiB、每图片响应最多 2 MiB；元数据累计响应上限 2 MiB。共享 HTTP 并发上限 6，连接超时 8 秒、单请求期限 12 秒、资料加载总期限 30 秒。角色最多显示 48 项，真人演员和制作人员分别最多 24 项。图片来源限定到服务的 HTTPS 图片域名，不跟随 HTTP 重定向。

这些约束不代表安装包内代码、偏好存储或进程内存归零。内存回收和 GPU 驱动释放由 Flutter、Dart 与操作系统调度。旧文件仍占用原有磁盘空间，本次不自动删除。

## 移除范围与维护成本

移除应用插件注册、目录、安装更新、脚本运行器、权限桥接、插件图片适配、打包工具、示例脚本、包清单和 API 文档；移除 `flutter_qjs_next` 及其 QuickJS 原生运行库依赖。Flutter 自身的平台插件（播放器、窗口、文件选择等）仍为核心平台适配的一部分。

没有新增第三方依赖，也没有额外打包素材、字体或离线数据库。偏好沿用 SharedPreferences，图片校验和并发限额复用现有实现。成本主要为两类服务的数据转换、开关状态和页面资源生命周期，避免继续维护通用动态脚本接口。

插件 GitHub 仓库由用户自行删除；删除前保存的 Git 镜像仅作为本地回退资料，不属于应用产物。历史研究文档已标记停止执行。

### 关闭后内存保留的进一步诊断（2026-11-08）

使用同一平板的独立 Profile 应用运行三组各 24 轮：原实现加载图片、原实现不加载图片、优化后加载图片。页面、HTTP、图片解码均走生产实现；网络数据由本机固定响应提供。诊断程序仅保存会话弱引用，在第 0、4、12、24 轮调用 VM 服务 GC，获取类存活统计、Dart 堆及 Android 内存分类。GC 和探针仅存在于测试入口，不进入正式应用。

三组所有检查点的 `OptionalPeopleSession`、人物页面/图片 State、HTTP 客户端、原生图片包装及 Codec 均为 0；唯一持续存在的原生 socket 是测试 HTTP 服务。关闭后没有新增功能请求，图片缓存及 live image 为 0。

| 场景 | 初始存活堆 | 第 4 轮 | 第 12 轮 | 第 24 轮 | 撤下测试页面后 |
|---|---:|---:|---:|---:|---:|
| 原实现，有图片 | 8.892 MiB | 8.929 MiB | 8.939 MiB | 8.956 MiB | 8.644 MiB |
| 原实现，无图片 | 8.891 MiB | 8.922 MiB | 8.935 MiB | 8.949 MiB | 8.638 MiB |
| 优化后，有图片 | 8.891 MiB | 8.926 MiB | 8.938 MiB | 8.955 MiB | 8.643 MiB |

检查点间的少量堆增长还包含测试程序不断追加的测量记录，不能把它算成功能泄漏。无图片组同样发生初期进程占用上升。内存未完全回落主要体现为堆容量、原生堆及图形内存的保留，而不是可选功能 Dart 对象继续存活；具体原生分配器与驱动缓存内部的占用归属，不能仅凭分类统计精确判断。VM 分析本身也会产生额外分配，原始记录同时保留 GC 前后数据，不能与无分析器的 Release PSS 直接比较。

图片相关优化限于 `ImageStore.validate`：复用已读取尺寸的 `ImageDescriptor` 与编码缓冲；校验用帧两轴最多 64 像素、不放大小图，并保证缩小后至少 1 像素。仍保留 6400 万源像素限制、真实首帧解码和异常处理，原始图片字节及正式显示尺寸不变。未改变 MPV/FFmpeg、字幕、视频色彩/渲染或播放器缓存，也未加入强制 GC、全局图片缓存清空或系统内存整理。

先新增回归测试，旧代码在 1×1、1×256 和 256×1 三种图片上失败：前两者被放大，后一种被缩成零高度后误报损坏。修复后三种及正常横图、损坏数据共 5 项通过。检查帧像素存储现在至多 16 KiB；这不代表整个解码器峰值只有 16 KiB，源图片与解码器内部工作区仍可能更大。每次校验消除一次重复编码缓冲创建。实测没有显示可靠的整体 PSS 降幅，不宣称本次优化可收回原先所有保留内存。

最终完整回归 367 项通过、8 项跳过，静态分析通过。原始分配统计、系统内存、对照日志及后续长轮次结果位于 `release/validation/optional-memory-20261108/`。

优化版追加 100 轮（约 7 分 34 秒、3,200 次固定服务请求）后，全部对象回收断言仍通过。第 24/60/100 轮 GC 后存活堆为 8.957/9.004/9.061 MiB；测试记录随轮数增长，撤下页面后为 8.747 MiB。图形内存为 152.50/153.05/153.42 MiB，原生堆 private 为 41.77/44.09/45.32 MiB。增速放缓，但后段仍有小幅增长，不能由此证明所有原生/驱动分配已完全稳定。GC 后没有可选功能的 Dart 对象、Codec、图片包装或 HTTP 客户端被持续持有，这与“整个进程的所有分配都不存在泄漏”是不同的结论。


低干扰对照另做 60 轮，仅初始、第 60 轮和撤页时获取完整堆统计。第 60 轮存活堆为 9.004 MiB，GC 后 PSS 为 193.80 MiB；频繁取快照的 100 轮实验在第 60 轮为 204.77 MiB。这是诊断开销的支持证据，但两次运行的分配器状态不同，不将约 11 MiB 差值全部认定为快照开销。

随后使用 [Perfetto 原生分配采样](https://perfetto.dev/docs/data-sources/native-heap-profiler)，并按 [Flutter 引擎符号化流程](https://flutter.googlesource.com/mirrors/flutter/+/HEAD/docs/engine/Crashes.md)匹配精确 Build ID `daebf50ff85b6ab57e09ce42aebd2c51394349f9`。首次启动期采样出现共享缓冲溢出，只保留失败记录，不作为内存结论。降低密度到 256 KiB 并在运行中附加后，取得约 44.62 秒无缓冲溢出的有效记录。最终采样统计中约 10.375 MiB 尚未观察到释放的 malloc 分配，约 8 MiB 对应 `GetAllocationProfileImpl → AllocationProfilePrintJSON → JSONWriter → TextBuffer::EnsureCapacity`：来源就是诊断接口生成的 JSON。其他样本包含 Dart 时间线元数据，以及 Impeller/Vulkan 文本绘制和图片上传路径。此结果确认分析工具会改变被测进程，不能把诊断版 PSS 上升直接归因于扩展代码。采样不包含附加前分配及直接 GPU 分配，也不能证明剩余驱动占用没有长期泄漏。
