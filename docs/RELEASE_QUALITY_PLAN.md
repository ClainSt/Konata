# CCPlayer 正式版改进与验收计划

目标是在每台设备上，以独立 mpv 播放同一份本地原片作为对照，交付画质接近参考、资源占用可控的正式版。UI 的长期目标是一次修改公共样式即可覆盖现有和以后接入的功能。以下门槛是拟定的工程验收条件，已完成的实验以现有报告为准。

## 1. 冻结可回退的正式版基线

- 记录源码版本、Flutter/libmpv 版本、ABI、签名、参考 mpv 配置、实际字体、显示器模式和手机型号。分开记录首次安装默认体验和本机已配置体验。本机 Windows 的字形对齐依赖独立 mpv 的可用字体，迁移机器时须重新核对。分享配置时仅包含字幕设置，不导入第三方脚本或凭据。
- 当前 release 清单中的旧版 Windows ZIP 约 35.6 MiB，解压约 83.9 MiB，Android ARM64 APK 约 37.0 MiB。Android 安装后占用、双端运行内存与缓存高水位须补测。清单记录 Android 使用调试证书；发布前核对既有用户的签名兼容性及目标分发渠道，再决定签名安排。
- 先从旧版正式包测量，再用同样数据、设备和动作测候选版。保留旧包、配置备份和数据库备份，升级及回退测试使用副本。

## 2. 先把已验证的播放效果交付到正式入口

| 项目 | 验收方法与决策 |
|---|---|
| 数据与视频 | 校验本地文件与真实 WebDAV 完整字节哈希，同机独立 mpv 本地、CCPlayer 本地、CCPlayer WebDAV 三路对照。记录解码输出、色域、范围、传递函数、缩放与最终画布。在相同 PTS、显示模式和缩放下比较暗部、雾气、细线；将字幕关闭单独测视频。可比且确实逐像素相同才写“完全一致”；不同的结果保存差图与误差。|
| ASS | 用《86》第一集 23:08.345 的双行歌词和 02:56.218 的定位字幕，记录 libass 实际字体、每行宽度、位置与遮罩重合度。回归基线为 Windows 双行宽误差各 1 px、Android 4／5 px，歌词遮罩交并比分别为 0.769、0.694。相同设备和配置复测，若超出重复测量波动，定位原因后再放行。另测内嵌字体、缺字、用户自选字体及无外挂字幕。|
| 流畅度 | Android 在同一 2.4 GHz 环境从片头播放整集，交替测试候选策略与原策略。分别报告冷／热起播、固定前后跳转至首个持续播放画面的耗时、缓冲次数与总时长、解码及呈现掉帧、音画时钟差。记录吞吐，避免把两次不同的网络条件算成收益。Windows 同验全屏、窗口、键鼠和拖动；Android 同验触控、旋转及前后台恢复。|
| 未解释的差异 | 先复测 Android 横移的可辨画面间隔 P95（上次独立 mpv 43.49 ms，CCPlayer 50.87 ms）。结合缓冲状态与呈现时间区分读取等待和帧调度。Windows 先保留通过验收的纹理输出，仅在 D3D11 对照能同时改善画面并通过字幕、交互和资源验收时更换默认值。|
| 格式边界 | 在同机补测 H.264、Hi10P、HEVC Main10、FLAC/AAC。HDR 在具备相应能力的屏幕上单列测试与结论。SDR 合成截图只能证明该阶段的输出；物理面板位深、HDR 输出与声光端到端同步各需独立验证。|

## 3. 让所有界面随功能增删保持同一风格

**外观由公共主题和公共组件负责，功能页面负责数据、操作与排列。** 沿用现有 Flutter 主题体系。先梳理真实页面的重复实现，边迁移边删除旧实现，每次迁移一个完整用户流程。

| 责任 | 现有落点与实施规则 |
|---|---|
| 主题偏好与公共样式 | 由 AppTheme 管理用户选择，由 NipaPlayStyle 和 Flutter ThemeData/component themes 统一产生配色、字阶、基础间距、圆角、控件尺寸、焦点、选中、禁用和错误状态。图标大小与明暗对比同处维护。新增样式先查现有定义；确有新的共性才补充。|
| 可复用控件 | 盘点 UniformActionBar、SettingsPanel、SettingsChoiceCard、PlayerDialog 以及标准 Flutter 控件。优先通过主题统一标准控件。相同交互若在多处重复，再在现有组件收敛变体。卡片、操作栏、弹窗和表单按用途复用，避免万能组件堆叠布尔开关。|
| 页面与导航 | 页面组合公共组件，只提供标题、数据、回调及可用状态。对同一功能散落在菜单、设置、路由的重复入口，在对应导航范围内统一来源；简单页面保持直接声明。新功能引用公共样式即可响应主题更新。删功能时一起移除入口、路由、文案和专用组件，检查剩余页面的空位和失效导航；涉及历史数据另做兼容决策。|
| 平台差异 | 共享视觉与状态规则，保留 Windows 顶栏、键鼠焦点和 Android 底部导航、触控反馈。播放覆盖层允许高对比度。详情页按可用空间布局，手机或分屏空间不足时跳过背景图加载。|
| 持续验证 | 先选媒体库、设置、详情、播放弹窗各一个代表画面，留存桌面／窄屏、明／暗主题的基准图；用少量组件测试覆盖公共状态及主题切换。每次新增、删除或调整功能，在变更审查中标明所复用组件、入口变化和必要的例外。改公共主题时同时复查上述页面。验收演练是在同一批页面修改一次公共间距或颜色，并删除一个测试入口，确认新旧页面同步、其余导航无空项。|

## 4. 按使用路径改善播放以外的功能

按以下顺序交付，每一条都从真实入口走通，覆盖失败、取消和重试。

1. 媒体源与扫描：本地、WebDAV、SMB 的连接诊断可区分鉴权、路径、网络失败；取消扫描可再次启动；重复扫描不重复入库。凭据由现有安全存储管理。
2. 媒体库与详情：核验搜索、排序、季集与特典分组、封面和多版本选择。对同一批样本重复扫描、元数据失败后重试，保留手工锁定的匹配与编辑结果。
3. 观看历史与同步：从详情播放、退出、换端、续播走完整流程；离线后重试不重复产生记录，明确进度冲突处理并验证。
4. 设置、备份与恢复：主题、语言、媒体源与播放器偏好按约定持久化；用旧库副本做升级、备份、恢复演练，验证手工匹配、观看历史及用户资源。记录哪些内容需要重新授权。

## 5. 贯穿每一步的源码与资源门槛

- 每个改动聚焦一个可验收行为，先查现有归属与调用者。优先复用 mpv、Flutter 和系统能力。对 main.dart、watch_page.dart、catalog.dart 等集中入口，遇到明确重复或职责冲突再按边界拆分；删除旧路径前搜索引用并跑关联测试。第三方补丁记录原因、影响及可移除条件。
- 每次候选构建记录 ZIP/APK、Windows 实际展开尺寸、Android 安装后代码／数据／缓存；检查重复 DLL、ABI、字体和测试资源。媒体样本、截图及诊断工具只进验证目录。新增依赖提交体积差和替代方案。
- 资源测试在同设备、同库、同条件下至少重复三次，分开记录空闲、浏览大库、播放、连续跳转、退出后稳定值。Windows 记录私有字节、工作集和可用的 GPU 指标；Android 记录 PSS、图形内存可得项及温升。记录峰值、中位数和重复进出后的走势，避免把系统文件缓存当泄漏。
- 按视频读前、预览、海报、元数据和日志分别列出容量、生命周期及清理方式。测试连续扫描、拖动与退出，确认并发可取消、临时数据可回收、后台下载能停止。用户媒体、手工资源和库数据单独保护。
- 首轮建立实测波动范围后确定各端预算。包体或安装占用相对基线有可重复增长，须逐项解释；运行峰值明显超过波动时复测定位；重复进出持续增长、缓存无上限、视频质量或核心功能可复现退化，停止发布并回退该项。正式包中不常驻详细诊断与截帧。

## 6. 交付顺序与完成条件

先做正式包与资源基线，随后完成正式入口的 SDR 与整集验收。UI 先迁移设置和媒体源作示范；再把媒体库、详情、历史和备份按流程迁移，同时验收业务行为。最后做双端升级、签名、可启动性与资源回归。每阶段留下同条件对照、已知差异和回退点。Windows 便携目录、ZIP、Android ARM64 APK 在 release 中同组交付，双端验收通过后更新 latest-build.json，再按发布规则清理旧包。
